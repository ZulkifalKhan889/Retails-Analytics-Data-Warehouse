Understanding Each Table
Customers

Purpose

Stores customer information.

Primary Key

customer_id

Important Observation

Initially there was confusion between

customer_id

and

customer_unique_id

At first it looked like customer_unique_id should be the Primary Key.

After analysing the dataset we understood:

Orders

Primary Key

Foreign Key

Important Observation

It does not store products.

At first this seemed strange.

Later we realised one order can contain many products.

That is why products are stored in another table.

Order Items

Purpose

Stores every product inside every order.

Important Discovery

This was the first table where there was no obvious single Primary Key.

Initial Confusion

Neither

order_id

nor

order_item_id

was unique.

Understanding

The combination

(order_id, order_item_id)

uniquely identifies each row.

This introduced the idea of a Composite Primary Key.

Business Lesson

One order can contain multiple products.

Instead of repeating order information many times, the database separates orders from products.

This avoids duplication and follows normalization principles.

Products

Purpose

Stores product information.

Primary Key

product_id

Observation

This table has no Foreign Keys because it is a master table.

It is referenced by the Order Items table.

Sellers

Purpose

Stores seller information.

Primary Key

seller_id

Observation

Another master table.

Referenced by Order Items.

Payments

Purpose

Stores payment information.

Important Observation

An order can have multiple payment records.

Because of this, payment information is stored separately from Orders.

This avoids adding columns such as

payment_type_1
payment_type_2
payment_type_3

which would be poor database design.

Reviews

Purpose

Stores customer feedback.

Primary Key

review_id

Foreign Key

order_id

Observation

Reviews are separated from Orders because customer feedback is a different business entity.

Product Category Translation

Purpose

Maps Portuguese category names to English.

Initial Thought

It looked like just another CSV.

Understanding

It actually behaves like a lookup table.

In our database design we may use it as a reference table to avoid duplicated category names.

Geolocation

This was the most confusing dataset.

Initial Thought

It had no IDs, no obvious Primary Key and no Foreign Keys.

Understanding

It is a lookup table that connects location information through ZIP code prefixes.

Customers and Sellers both store ZIP code prefixes.

The geolocation table translates those ZIP prefixes into:

Latitude
Longitude
City
State

Potential Improvement

The dataset contains duplicate ZIP prefixes.

Later in the project we may create a cleaned location dimension so it can be used efficiently in MySQL and Power BI.

Database Architecture We Discovered

Instead of memorising relationships, we understood the business flow.

Customer

↓

Order

↓

Biggest Lessons Learned Today
Understand the business before designing the database.
Every table should have one clear responsibility.
Master tables store reference information.
Transaction tables record business events.
Composite Primary Keys exist when one column cannot uniquely identify a row.
Many-to-many relationships are solved using junction tables such as Order Items.

# Engineering Discussion 1 – Understanding One-to-Many Relationships

## Why We Discussed This

Before designing a relational database, it is important to understand how business entities are connected.

Instead of memorizing relationships, the goal was to understand *why* those relationships exist in the real world.

---

## Initial Understanding

At first, I understood that one category could contain multiple products, but I was unsure why a separate Category table was necessary instead of simply storing the category name inside the Products table.

---

## Business Scenario

Imagine an online store with the following products.

| Product | Category |
|----------|----------|
| iPhone | Electronics |
| MacBook | Electronics |
| AirPods | Electronics |

If the category name is stored inside every product record, the value "Electronics" is repeated many times.

This creates duplicated data.

---

## Problem

If the business decides to rename the category from

Electronics

to

Consumer Electronics

every product belonging to that category must be updated.

For thousands of products this becomes inefficient and increases the chance of inconsistent data.

---

## Better Database Design

Create a separate Category table.

Category

category_id (PK)

category_name_pt

category_name_en

Products

product_id (PK)

category_id (FK)

Now every product references the category instead of storing the category repeatedly.

---

## Relationship

One Category

↓

Many Products

This is called a One-to-Many relationship.

One parent record can have many child records.

Each child record belongs to exactly one parent.

---

## Lesson Learned

One-to-Many relationships reduce duplicated data and improve database maintenance.

Instead of storing repeated information, relational databases store it once and connect tables using foreign keys.

---

# Engineering Discussion 2 – Understanding the Translation Table

## Initial Confusion

The dataset contains a table named

product_category_name_translation

Unlike the other tables, it contains no obvious ID column.

This raised the question:

"If there is no ID, how is this table connected to the database?"

---

## Investigation

The table contains two columns.

product_category_name

product_category_name_english

The Portuguese category name is unique.

Therefore, within the original dataset it behaves as a Natural Primary Key.

Products reference this text value directly.

---

## Original Dataset Design

Products

product_category_name

↓

Translation Table

product_category_name (Natural Primary Key)

↓

English Translation

Although this works correctly, it means the relationship is built using text instead of an identifier.

---

## Engineering Improvement

Instead of using text as the identifier, a production database would normally introduce a Category table.

Category

category_id (PK)

category_name_pt

category_name_en

Products

category_id (FK)

This approach provides a stable identifier while allowing additional category information to be added in the future.

---

## Why This Design Is Better

• Easier to maintain

• Avoids using long text as foreign keys

• Easier to index

• Supports additional category metadata

• More scalable if the business grows

---

## Lesson Learned

The dataset represents one possible implementation.

A database engineer should evaluate whether the existing design is suitable or whether it can be improved.

# Engineering Discussion 3 – Composite Primary Key vs Surrogate Primary Key

## Question

The Order Items table currently uses

(order_id, order_item_id)

as a Composite Primary Key.

Should this design be kept?

Or should it be replaced with a single surrogate key?

---

## Initial Thought

At first, the idea of introducing a single Order Item ID seemed simpler because every row would have one unique identifier.

---

## Analysis

The existing composite key already uniquely identifies every product inside an order.

Example

Order 100

Item 1

Item 2

Item 3

The combination

(order_id, order_item_id)

already has real business meaning.

It naturally represents the position of a product inside an order.

---

## Alternative Design

Order_Items

order_item_id (PK)

order_id (FK)

product_id (FK)

seller_id (FK)

price

freight_value

This design is commonly used in production systems because many frameworks and APIs prefer a single-column primary key.

---

## Final Decision for This Project

The composite primary key will be retained.

Reason:

The goal of this project is to model the business accurately while demonstrating an understanding of composite keys.

An alternative surrogate key design was considered, but introducing an additional identifier would not provide significant value for this analytics database.

---

## Lesson Learned

Not every table requires a surrogate key.

Composite Primary Keys are completely valid when they naturally represent the business process.

A good database design is based on business requirements rather than personal preference.

---

# Key Takeaways

At this stage, the focus shifted from analysing CSV files to thinking like a database engineer.

Important lessons learned:

✓ Every relationship should represent a real business process.

✓ Database design should minimize duplicated data.

✓ Foreign Keys connect related entities.

✓ Lookup tables improve consistency.

✓ Composite Primary Keys are sometimes better than introducing artificial IDs.

✓ A dataset should never be copied blindly.

Instead, every design choice should be questioned and justified before implementation.

# Objective

# Engineering Discussion 1 – What is an ER Diagram?

## Initial Thought

Initially, I thought an ER Diagram was simply boxes connected with lines before creating tables.

After discussion, I understood that an ER Diagram is much more than a drawing.

It is the blueprint of the entire database.

Just as a building requires an architectural blueprint before construction begins, a database requires an ER Diagram before implementation.

Business Requirements

↓

ER Diagram

↓

Database Schema

↓

MySQL Implementation

Without a proper blueprint, the database may work initially but become difficult to maintain and expand.

---

## What an ER Diagram Contains

Every ER Diagram contains four main components.

### 1. Entities

Entities represent real-world business objects.

Examples from this project:

- Customer
- Orders
- Products
- Sellers
- Payments
- Reviews
- Categories
- Locations

A simple way to identify entities is to read the business requirements and circle the nouns.

Example:

Customer places an Order.

Order contains Products.

Customer leaves a Review.

The nouns become entities.

---

### 2. Attributes

Attributes describe an entity.

Example:

Customer

- customer_id
- customer_city
- customer_state

These later become the columns inside a database table.

---

### 3. Relationships

Relationships explain how two entities are connected.

Examples:

One Customer → Many Orders

One Order → Many Order Items

One Category → Many Products

Relationships should always represent a real business process.

---

### 4. Keys

Every entity requires a way to identify each record.

Examples include:

- Primary Keys
- Foreign Keys
- Composite Primary Keys
- Natural Keys

Keys ensure data integrity and allow tables to be connected.

---

# Lesson Learned

An ER Diagram is not simply a picture.

It is the complete blueprint of the database and should always be designed before writing SQL.

# Engineering Discussion 10 – Relationship Type vs Participation

One misunderstanding occurred when discussing mandatory relationships.

Initially, I confused

One-to-Many

with

Mandatory Relationships.

These are different concepts.

Relationship Type answers

"How many records are related?"

Participation answers

"Can this record exist without another record?"

Example

A Customer can exist without placing an Order.

This relationship is optional for Customer.

However,

an Order cannot exist without a Customer.

This relationship is mandatory for Order.

---

# Lesson Learned

Relationship type and participation are completely different concepts.

Both must be considered when designing an ER Diagram.

# Phase 3 – Physical Database Design

---

# Objective

After completing the Logical ER Diagram, the next step was understanding how a logical design is converted into a real database.

At first, I thought creating tables in MySQL was simply choosing column names and data types.

However, I learned that professional database design requires making engineering decisions before writing any SQL.

For every table, a database engineer should ask:

- Why does this table exist?
- What business problem does it solve?
- What is the Primary Key?
- Why was that Primary Key chosen?
- Which data type is most appropriate?
- Which constraints are required?
- Which columns should be indexed?
- Can the design scale as the business grows?

Only after answering these questions should the table be implemented.

---

# Engineering Exercise – Designing the Customer Table

To understand the process, the Customer table was designed completely before moving to MySQL.

Instead of immediately writing SQL, every column was questioned.

---

# Step 1 – Understanding the Purpose

The Customer table exists to store customer information.

Its responsibility is only customer-related data.

It should not contain orders, payments or reviews because those belong to different business entities.

This follows the Single Responsibility Principle.

---

# Step 2 – Analysing Every Column

The dataset contains five columns.

- customer_id
- customer_unique_id
- customer_zip_code_prefix
- customer_city
- customer_state

Instead of accepting them without question, every column was analysed.

---

## customer_id

### Initial Confusion

At first, I was confused because another column called `customer_unique_id` already existed.

I thought that if a unique customer identifier already exists, then `customer_id` seems unnecessary.

---

### Investigation

After analysing the Orders table, I discovered that Orders do not reference `customer_unique_id`.

Instead, every order references `customer_id`.

This means `customer_id` identifies the customer record attached to a specific order.

Example:

Real Customer

↓

customer_unique_id = U100

↓

Order 1

customer_id = A1

↓

Order 2

customer_id = C3

Although both records belong to the same real customer, each order has its own customer record.

---

### Why Does Olist Do This?

This design preserves historical information.

Imagine a customer places an order while living in São Paulo.

Months later the customer moves to Rio and places another order.

If only one customer record existed, the original address could be lost or overwritten.

By creating a separate `customer_id` for each order-level customer record while keeping the same `customer_unique_id`, historical customer information remains associated with the correct order.

---

### Final Decision

- Data Type: CHAR(32)
- Constraint: PRIMARY KEY
- Constraint: NOT NULL

The values are always 32 characters long, making CHAR(32) a better choice than VARCHAR(32).

---

## customer_unique_id

### Purpose

This column represents the real customer across multiple purchases.

Unlike `customer_id`, which identifies an order-level customer record, `customer_unique_id` identifies the actual person.

This makes analyses such as:

- Customer Lifetime Value (CLV)
- Repeat Customer Analysis
- Customer Retention
- Churn Analysis

possible.

Without this column, every order would appear to belong to a completely new customer.

---

### The Trick Question

One important question was asked during the design process.

Should `customer_unique_id` have a UNIQUE constraint?

Initially, the obvious answer seemed to be "Yes" because the column name contains the word "unique".

However, this assumption is incorrect.

Example:

| customer_id | customer_unique_id |
|--------------|-------------------|
| A1 | U100 |
| B2 | U200 |
| C3 | U100 |

The same customer (`U100`) appears more than once because the customer placed multiple orders.

If a UNIQUE constraint were applied, the database would reject the third row.

This demonstrates an important lesson:

The word "unique" in a column name does not necessarily mean the values must be unique within that table.

Instead, `customer_unique_id` uniquely identifies the real person, while the table intentionally stores multiple records for that person.

---

### Final Decision

- Data Type: CHAR(32)
- Constraint: NOT NULL
- UNIQUE Constraint: Not Applied

---

# Engineering Lessons Learned

Several important lessons were learned from designing only one table.

### Lesson 1

Never choose a data type without a reason.

Every data type should be justified.

Example:

CHAR(32) was selected because every identifier has a fixed length.

---

### Lesson 2

Never assume a column's purpose from its name.

Understanding how a column is used across the database is more important than its name.

The `customer_unique_id` column is the perfect example.

---

### Lesson 3

Primary Keys should represent how the business identifies records.

The Orders table references `customer_id`, making it the correct Primary Key even though another identifier exists.

---

### Lesson 4

Database design is driven by business requirements rather than technical preferences.

Understanding how the business operates should always come before writing SQL.

---

# Final Reflection

Before this phase, I believed physical database design meant deciding column names and data types.

After completing this exercise, I understood that physical design is actually a process of making engineering decisions.

Every column, constraint and data type should have a clear business justification before implementation begins.

This phase changed the way I think about designing databases and provided a repeatable methodology that can now be applied to every remaining table in the project.
